# Decisions

Every choice we made, what else we could have done, and why we picked what we did.
Format for each: **Chose**, **Alternatives**, **Why**. Numbers quoted here come from
[RESULTS.md](RESULTS.md), which is generated by a script.

---

## Part 1: Technology

### T-1. Language: Python 3, standard library only
- **Chose:** Python 3.9+ with zero third-party packages for the engine, server and tests.
- **Alternatives:** Python with numpy/pandas; TypeScript/Node end to end; Rust or Go for speed.
- **Why:** The venue Wi-Fi is unreliable, so `pip install` at the venue is a risk we removed entirely.
  The AIML judges read Python fluently, which matters when they ask "show me the bid formula".
  Speed isn't a problem: one step with 24 agents takes about 0.8 ms (RESULTS.md, Scalability),
  so numpy would add a dependency and buy nothing.

### T-2. Web server: built-in `http.server` (ThreadingHTTPServer)
- **Chose:** Python's built-in HTTP server with a ~150-line JSON API.
- **Alternatives:** FastAPI or Flask; WebSockets for streaming steps.
- **Why:** One presenter, one browser tab, localhost only. A framework would need an install
  and teaches the judges nothing about our idea. The browser asks for the next step each tick
  (simple polling), which also makes pause, step and speed trivial: the browser controls the pace.

### T-3. Dashboard: vanilla JavaScript and hand-drawn SVG charts
- **Chose:** Plain HTML, CSS and JS; charts drawn as SVG paths in about 250 lines (`web/charts.js`).
- **Alternatives:** React + Vite + a chart library (Recharts or Chart.js); loading libraries from a CDN.
- **Why:** No build step and no CDN means it works offline from one command. Drawing the chart
  ourselves let us draw exactly the picture our idea needs. The hatched *deficit wedge* (requested
  minus supplied) is the shortfall the agents negotiate over, and stepped areas match 15-minute
  steps. A stock chart library would have pushed us toward a generic line chart.

### T-4. Fonts: IBM Plex, self-hosted
- **Chose:** IBM Plex Sans and Mono `.woff2` files committed in `web/fonts/` (SIL Open Font License).
- **Alternatives:** Google Fonts link; system fonts.
- **Why:** A Google Fonts link fails offline. Plex has true tabular numerals, so columns of kW
  values line up and don't jitter while the simulation runs.

### T-5. Tests: `unittest` (standard library)
- **Chose:** 69 tests with `unittest`, run with `python3 gridpact.py test`.
- **Alternatives:** pytest; Hypothesis for property-based testing.
- **Why:** Same reason as T-1: nothing to install. We hand-wrote the property-style tests we
  needed, for example 3,000 random cases fuzzing the fallback, and every scenario × policy × seed
  checked for capacity violations.

### T-6. Scenarios and agents as JSON files
- **Chose:** `data/scenarios/*.json` and `data/agents/*.json`, validated on load (`config.py`).
- **Alternatives:** Python dicts in code; YAML.
- **Why:** The problem statement asks for scenarios as data. JSON is in the standard library (YAML isn't).
  Adding a fifth utility or a new disaster means editing a file, not code. Bad values (min > desired,
  an event naming an unknown agent) stop the program at startup with a clear message.

### T-7. Power on the wire is integer watts
- **Chose:** Supply, requests and allocations are `int` watts. Reserves and physics use float kW/kWh.
- **Alternatives:** Floats in kW everywhere; Python `Decimal`.
- **Why:** The hard guarantee is "zero capacity violations". With floats, `0.1 + 0.2 > 0.3` is true,
  so a validator could pass or fail on rounding noise. Integer comparison is exact. Requests round
  *down* (never ask for more than you need), but the survival floor rounds *up* (never under-state
  what keeps you alive). We found this bug ourselves: rounding the floor down made an agent fail
  by 0.4 W.

### T-8. Immutable state (frozen dataclasses) and a single-assignment commit
- **Chose:** All state records are `@dataclass(frozen=True)`. A step builds new objects and commits with `self.state = candidate`.
- **Alternatives:** Mutate state in place and write undo logic; deep-copy then restore on error; a database transaction.
- **Why:** If nothing is ever modified in place, "rollback" is free: on any error we simply don't
  do the final assignment. That one line is the whole atomic-commit mechanism, and it's easy to
  explain and easy to test (we crash the step at 6 different points and check that the state
  object is identical).

### T-9. Optional LLM narration via the official `anthropic` SDK, off by default
- **Chose:** `gridpact/narration.py`, active only with `GRIDPACT_LLM=1`. The SDK is imported lazily,
  model chosen with `GRIDPACT_LLM_MODEL`, low effort.
- **Alternatives:** No narration; making it a core feature; raw HTTP calls.
- **Why:** The brief says the core must never depend on it. The SDK import happens inside the
  function, so the simulator runs without the package. Any failure (no package, no key, no
  network) returns a message instead of raising. We verified this against the real SDK (2.8.0):
  with no credentials the SDK raises a `TypeError` before any request, which our first version
  didn't catch. Narration now catches every exception, and a test covers it. A test checks that a normal run never imports
  the SDK. The narrator only paraphrases the finished, deterministic log; its text never feeds
  back into allocation.

## Part 2: Algorithm

### D-1. One agent object per utility, with truly private state
- **Chose:** `UtilityAgent` holds config and decision rules. Its `AgentState` (reserve, credits,
  streaks) is passed only to that agent's own methods. During rounds, agents see a `PublicRound`
  with offers, floors and bids only.
- **Alternatives:** One central optimizer that reads everyone's state; agents that share full state.
- **Why:** The problem asks for decentralized agents that "decide their own bids and concessions
  from their own state plus public info". A test checks that no agent method takes another
  agent's state, and that `PublicRound` has no private fields.

### D-2. Requests carry a reserve-aware survival floor
- **Chose:** `request.max = desired + reserve top-up`; `request.min = critical load − what my backup can supply now`.
- **Alternatives:** Requests of just (min_kw, desired_kw) from config.
- **Why:** Reserves are what let an agent afford to concede. A hospital with a full diesel tank can
  survive on less grid power than one with an empty tank, so the agent's announced need *should*
  depend on its reserve. This is the single biggest reason GridPact beats the baselines.
  Proportional and strict priority don't use it.

### D-3. Bid formula: multiplicative urgency
- **Chose:** `u = weight × (1 + e·streak) × (1 + 2·(1 − reserve fraction)) × (1 + 0.1·credits)`, capped at 50.
- **Alternatives:** An additive score; a learned (ML) bid; a plain priority rank.
- **Why:** Each factor answers a judge-friendly question. *How critical am I?* (weight). *How long
  have I been short?* (escalation). *How much backup do I have left?* (scarcity). *Have I given
  way before?* (credits). Multiplying means a factor matters in proportion to the others:
  doubling escalation doubles urgency, whatever the weight. A learned bid would be a black box we
  couldn't defend, and we have no real data to train on. The cap of 50 bounds what a lying agent
  can claim.

### D-4. Concession rule: split the excess by 1/urgency, in increments
- **Chose:** Each round, each agent that can still concede gives `(1/u_i) / Σ(1/u_j)` of the remaining
  excess, capped at 25% of its slack per round.
- **Alternatives:** Concede in fixed kW steps; the lowest bidder concedes everything first (an auction);
  everyone concedes the same percentage.
- **Why:** 1/u means the least urgent gives the most, but everyone with slack gives *something*, so
  no single agent is wiped out in one round. Shares sum to 1, so concessions never overshoot.
  The 25% cap creates real rounds (mean 3–4 per contested step) that a judge can watch in the log,
  and gives the excess time to shrink. An all-or-nothing auction is what starves low-priority
  utilities.

### D-5. Two phases: hold firm, then dig into reserves
- **Chose:** Phase 1: an agent below 30% reserve *holds firm* at its full critical load. Phase 2
  (only if phase 1 deadlocks): everyone may go down to its reserve-backed floor.
- **Alternatives:** A single phase where everyone always uses reserves; never use reserves during negotiation.
- **Why:** This is "agents near failure hold firm" from the brief, made precise. Agents with
  healthy reserves sacrifice first; the last 30% of a reserve is protected until there is no other
  way. In the cyclone that ordering is the difference between 0 failure events (GridPact) and 2
  (proportional).

### D-6. Discharge policy: protect the last half of the reserve
- **Chose:** Above 50% reserve, the backup covers the full desired load. Below 50%, it covers only critical load.
- **Alternatives:** Always cover desired load; always cover only critical load.
- **Why:** In a 24-hour disaster, burning diesel on comfort load at hour 3 means failing at hour 10.
  This rule is part of the agent and applies identically under every policy (baselines get the
  same physics), so it isn't what makes GridPact win.

### D-7. Round cap: 16
- **Chose:** At most 16 rounds per step, then the fallback.
- **Alternatives:** No cap; a time limit in milliseconds.
- **Why:** The brief requires a cap. With 25% increments, each phase needs at most about 4 rounds
  of capped concession, plus a few share-limited rounds. The observed maximum is 9 rounds
  (RESULTS.md), so 16 leaves headroom while still bounding latency. A time limit would break
  determinism, because results would depend on machine speed.

### D-8. Deterministic fallback: survival floors by urgency, then top-up
- **Chose:** Sort by bid (ties by id), give each agent its survival floor while supply lasts, then top up in the same order.
- **Alternatives:** Proportional scaling; strict priority; random selection.
- **Why:** It must be deterministic (same input, same output) and safe by construction. Giving
  survival floors first keeps the most utilities alive. Ordering by the agents' *own announced*
  bids means even the fallback respects what the agents said, not a central ranking. In the 4
  main scenarios the fallback was never needed (0 fallback steps, RESULTS.md). It exists for
  deadlocks and for the validator-rejection path, and both are tested.

### D-9. Fairness credits are a relative ledger
- **Chose:** `Δcredits = 10 × (my concession share − average share)`, clamped to [0, 20].
- **Alternatives:** Absolute credits per kW conceded (our first version); no credits; credits that only decay.
- **Why:** Our first version paid credits for every kW conceded. In a real crisis *everyone*
  concedes, so every agent hit the cap within a few hours. Equal credits cancel out in the 1/u
  shares, so they stopped doing anything. We saw it on the dashboard and changed it. The relative
  ledger rewards only *above-average* sacrifice, and an agent that gave less pays back. Credits
  stay informative for the whole run.

### D-10. The validator checks physics only
- **Chose:** 4 checks: agent set, integer watts, 0 ≤ a ≤ request, Σa ≤ supply. It never sees bids or damage.
- **Alternatives:** A validator that also enforces priority or fairness rules.
- **Why:** This answers "isn't the validator just a central controller?". It can't pick winners,
  because it has no information to pick with. It only says "physically allowed" or "not allowed".
  The metrics module re-checks capacity independently from raw watts, so a validator bug couldn't
  hide a violation.

### D-11. Determinism: noise is a pure function of (seed, step)
- **Chose:** `random.Random(seed × 1,000,003 + step)` for each step's supply noise. Injected events are recorded with their step.
- **Alternatives:** One shared random generator for the whole run.
- **Why:** A shared generator's position is hidden state. After a rollback you'd have to rewind it
  too, or the run would no longer replay. Per-step seeding has nothing to rewind. Recording
  injected events with their step means a live demo (with buttons pressed) replays
  byte-for-byte; the comparison view re-runs every policy with exactly those events.

### D-12. Damage function: weighted, two-tier, escalating
- **Chose:** `weight × (1 × comfort gap + 6–8 × critical gap) × (1 + e × consecutive short steps) × Δt`.
- **Alternatives:** Count failures only; linear kWh unserved.
- **Why:** The brief asks for harm that grows the longer a load goes unserved. Two tiers capture
  that losing ICU power is far worse than losing air-conditioning. Escalation makes a 6-hour
  outage much worse than six separate 1-hour outages, which is what prevents starvation in the
  *objective*, not just in the protocol.

### D-13. Cascades: effectiveness loss over a dependency graph
- **Chose:** Edge `source → target, impact`: if the source fails, the target's effective service drops by `impact × its desired load`. Iterated to a fixed point.
- **Alternatives:** A fixed damage multiplier on the target; no cascades.
- **Why:** One knob, physically meaningful ("without telecom, dispatch is 35% less effective"), and
  it can push the target below its own minimum, so failures genuinely chain. The iteration only
  ever adds failures, so it terminates even with cycles (tested).

### D-14. Baselines: equal split, proportional, strict priority
- **Chose:** The three named in the brief, with identical requests, physics and validator.
- **Alternatives:** Also an optimal linear program (LP) as an upper bound.
- **Why:** Only the allocation rule differs, so the comparison is fair. We did not include an LP
  optimizer. It is a valid future comparison, but it needs a solver package (T-1) and assumes one
  party sees everyone's private state, which is the centralization the problem asks us to avoid.
  See JUDGE_QA Q2.

### D-15. Jain's fairness index on mean service ratio
- **Chose:** Jain's index over each utility's average (effective served ÷ desired) for the run.
- **Alternatives:** Jain's index per step, then averaged; Jain's index on raw kW.
- **Why:** Raw kW would call it "unfair" that a hospital uses more than a telecom tower. Service
  ratios compare like with like. We report it honestly: proportional scores slightly higher
  (0.9993 vs 0.9992) because it gives everyone the same ratio, while GridPact deliberately tilts
  toward critical load to prevent failures.

### D-16. Dashboard design
- **Chose:** A dark control-room interface. Ivory for the system's own voice (supply line, primary
  actions); amber and red only for real trouble. Agent colours by utility *kind*, in an order that
  passes a colour-blindness validator. A guarantees strip that is always visible. An outcome-first
  negotiation log.
- **Alternatives:** A generic admin template; one colour per agent cycled from a palette.
- **Why:** Judges see a laptop for about a minute. The guarantees (0 violations, steps committed,
  4/4 checks) must be visible at all times. Colour follows the utility kind, so a hospital is
  always blue in every scenario, and status is never shown by colour alone (each status has an
  icon and a label). The three baselines run in lockstep with the live run, so the comparison is
  visible *during* the demo, not only on the results tab. The design went through Impeccable's
  audit, a two-reviewer critique and a polish pass.

### D-17. Bids carry the agent's own harm rate; concessions are a fraction of slack
- **Found by:** running the protocol on real Mumbai numbers ([CITY.md](CITY.md)). There,
  hospitals (37 MW), water pumping (50 MW) and the mobile network (15 MW) sit next to 3,228 MW of
  homes and businesses. Under the original rule GridPact did **2–4× more harm than strict
  priority** in all four disasters, with no failures and no violations: it was simply making the
  wrong trade.
- **Two biases:** (1) The bid ignored *how much harm a kW does*. Every core utility has the same
  comfort-harm rate (1.0), so the bid never needed it, but on a real city a kW cut from water
  pumping does ~10× the harm of a kW cut from homes. (2) Each agent conceded a share of the
  excess *in absolute watts* (∝ 1/u). Next to a 3,000 MW load with a similar bid, a 37 MW
  hospital's "share" exceeded its whole load, so it always gave up everything.
- **Chose:** u gains the agent's own `damage_soft` (private config it already owns), and a
  round's share becomes ∝ slack/u: a fraction of what you can give. Both use only the agent's
  own state plus public offers, floors and bids, so the protocol stays decentralized.
- **Alternatives:** keep the rule and report the city result as a limitation; or add only the
  harm term (core results byte-identical, but Mumbai still +33–47% vs strict priority).
- **Cost, measured:** core advantage vs the best baseline moved from −16/−4/−8/−9% to
  −15/−2/−7/−5% (cyclone / cascading / heatwave / metro, 10 seeds), still 10/10 seeds and 0
  failure events everywhere. Mumbai moved from +104…+308% to within ±0.4% of strict priority.
- **Why that is the ceiling on Mumbai:** when the critical sectors are ~3% of load, any policy
  that protects them first (strict priority, equal split) is close to optimal, and the remaining
  harm is homes losing power, which no allocation can avoid. GridPact matching it while still
  beating proportional by up to 12% is the honest result.

### D-18. The deadlock fallback grants whole floors only, and voids deadlocked concessions
- **Found by:** the Mumbai intensity sweep. At 1.25× the 2020 loss, 137 MW remained, about the
  size of the critical services. Homes needed 424 MW to avoid failing, so the negotiation
  deadlocked. Hospitals, water and telecom had already conceded to zero trying to make room. The
  fallback then gave homes all the power (a partial floor, so they failed anyway) and capped
  everyone else's top-up at their conceded-to-zero offers. GridPact came out 6.9% worse than
  strict priority.
- **Chose:** (1) grant a survival floor only if all of it fits; (2) after a *deadlock*, top up
  toward each agent's original request, because concessions offered for an agreement that cannot
  exist are void. After a *round cap* the converging offers still bound the top-up.
- **Why it's safe:** the fallback is still constraint-safe by construction (every grant clipped
  to [0, request.max], taken from what remains), and it is still fuzz-tested over 3,000 random cases.
- **Effect, measured:** the fallback never ran in the core scenarios, so their results are
  unchanged. At 1.25× on Mumbai, GridPact went from +6.9% to +0.1% vs the best baseline. The
  lying-agent experiment (which forces deadlocks) changed, and RESULTS.md reports the new numbers.
